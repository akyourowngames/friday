# Existing Tools Upgrade Matrix (2026-07-16)

Source: `Upgrade Features Inside Ares’s Existing Tools.pdf`.

## Contract and implementation rules

- Existing public tool names remain stable. New behavior is exposed through optional parameters and modes.
- Existing calls retain legacy defaults. Major behavior changes are gated by `tools.advanced_*` feature flags and/or an explicit `response_format="structured"` request.
- Structured responses use one envelope: `ok`, `status`, `summary`, `data`, `artifacts`, `warnings`, `errors`, `next_actions`, `provenance`, `metrics`, and `undo_id`.
- SQLite migrations are additive and idempotent. Destructive rewrites are not used.
- Mutating tools continue through the current authorization, confirmation, path-boundary, action-ledger, and optimistic-concurrency controls.
- Tests are split by family, plus schema/backward-compatibility and structured-envelope regression suites.

Legend: **S** small, **M** medium, **L** large, **XL** cross-cutting.

## Delivery sequence and commit gates

1. Matrix and shared internal response/validation primitives.
2. Memory and People.
3. File and runtime.
4. Web and research.
5. Cron, Watcher, and Phone.
6. Delegation, Skills, and MCP.
7. Images, action history, and export.
8. Shared structured-response rollout, documentation, targeted family suites, then full regression.

Each gate requires: schema tests, implementation tests, backward-compatible legacy tests, structured-envelope tests, permission/confirmation regression tests, `git diff --check`, and a dedicated commit pushed to the draft PR.
